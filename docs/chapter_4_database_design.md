# Chapter 4: Database Design

## 4.1 Introduction
The Cardiovascular Disease Risk Prediction System distinguishes itself from traditional web applications by employing a highly secure, privacy-preserving stateless architecture. In the context of healthcare technology, handling Protected Health Information (PHI) requires stringent security protocols, encryption, and compliance measures. By deciding not to persist user data in a traditional relational or NoSQL database, the system entirely mitigates the risks associated with data breaches and unauthorized access. All clinical inputs provided by the user are processed strictly in memory during the prediction cycle and are immediately discarded once the risk score is generated. This chapter outlines the logical data structures used during runtime and proposes a database schema that could be implemented if the project scope is expanded to include user authentication and historical tracking.

## 4.2 Purpose and Scope
The primary purpose of the data design in the current system is to ensure the efficient transport and transformation of 13 specific clinical variables from the user interface to the machine learning model. The scope involves defining strict data types, enforcing input limits, and standardizing JSON structures for API communication. While a physical database is absent, the structural integrity of the data passed through the system is rigorously maintained exactly as it would be within a strongly typed database schema.

## 4.3 Proposed Database Architecture (For Future Scope)
Should the application be expanded to support registered users who wish to track their cardiovascular health over time, a relational database (such as PostgreSQL) would be utilized. The system uses a simple, two-table architecture to keep relations straightforward.

### 4.3.1 Users Table
This table stores the authentication credentials and basic profile information.
- `user_id` (Primary Key, UUID)
- `email` (String, Unique)
- `name` (String)
- `created_at` (Timestamp)

### 4.3.2 Predictions Table
This table stores the risk assessments linked to a specific user. Instead of separating all 13 clinical parameters, they can be stored as a single JSON object to keep the schema clean.
- `prediction_id` (Primary Key, UUID)
- `user_id` (Foreign Key -> Users.user_id)
- `clinical_data` (JSON Object): Contains all medical inputs (age, BP, etc.)
- `risk_score` (Float): The final probability percentage generated by the AI model.
- `created_at` (Timestamp)

### 4.3.3 Relationships
- **1-to-N (One-to-Many):** One User can have Many Predictions.

## 4.4 Data Handling Approach
In the current implementation, the "database" is entirely ephemeral. 
- **Transient State Management:** The React frontend utilizes React State and Context APIs to temporarily hold the user's input as they navigate through the multi-step form. 
- **In-Memory Processing:** Once submitted, the Node.js API gateway receives a structured JSON payload. This data is held in the server's RAM just long enough to construct the multi-dimensional tensor required by the ONNX Runtime. Once the ONNX engine returns the output probability, the memory is cleared.
- **Client-Side Persistence:** The generated PDF report acts as the sole "hard copy" database for the user. By generating the report entirely on the client side using `jsPDF`, the user can save their results locally without any data ever being written to a server-side hard drive.
